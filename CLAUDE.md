# vagas — notas para o Claude

Ferramenta pessoal de auto-candidatura (Python 3.12 + Patchright/Playwright + OpenAI + SQLite). Leia o README para o fluxo. Idioma do usuário: pt-BR.

> **Esta é uma cópia limpa para uso de outra pessoa.** Não há perfil, banco, currículos nem sessões de
> navegador: o primeiro comando é `vagas setup` (`src/vagas/setup.py`), que pergunta cada dado e escreve
> `config/profile.yaml` + `.env`. As notas abaixo vieram de meses de uso real e são o motivo de a
> ferramenta funcionar nos ATS brasileiros — trate-as como o histórico de calibração do projeto.
> As "regras fixas" e os aprendizados citam decisões do usuário ANTERIOR; o que é preferência
> (pretensão, diversidade, empresas na blacklist, exigir ou não inglês) sai do perfil e do
> `settings.yaml` do novo dono, não do código. O que é regra de código está marcado como tal.

## Regras fixas pedidas pelo usuário (não relaxar)
- **Mudado pelo dono atual em 2026-10-29 (pediu muito mais volume):** teto de idade 24h -> **72h** (`HARD_MAX_AGE_HOURS`, `discovery.max_age_hours`); só remoto, **exceto presencial/híbrido em BH e região** (`discovery.local_cities`, buscas locais com `discovery.local_location` sem `f_WT`, raio 40 km; `Pipeline._in_local_area` olha `job.location` + `classification.job_city`, nunca a descrição); teto 300/dia (LinkedIn continua 50); janela 06:00–23:59; descoberta a cada 45 min; 144 buscas (7 base + 12 stacks × júnior/pleno/sem nível × 2 fontes + 30 locais), 5 páginas cada. Continuam bloqueados por escolha dele: vaga em inglês, sênior, BairesDev (e Jobbol). Regra de formulário "disponibilidade presencial" → Sim quando a vaga é presencial/híbrida (só passa se for na região).
- Só vagas das últimas 24h e só remoto: `config.py` (`HARD_MAX_AGE_HOURS`, `HARD_REMOTE_ONLY`), checadas em `pipeline.discover/prepare` antes de gastar IA.
- Só descrições em pt-BR (`filters.job_languages` + `pipeline.guess_language` sem IA). Inglês do usuário é avançado, mas ele não quer vagas em inglês.
- Descoberta do LinkedIn pelo endpoint público (`sources/linkedin.py: search_guest/fetch_details` com geoId 106057199); conta logada só para candidatar.
- Salário: valor da vaga se informado, senão `facts.salary_expectation_<nível>_<regime>` (`qa.py: salary_answer`).
- Anos por nível: pleno = metade, júnior = 1/4 (`resume/profile.py: scale_profile_for_seniority`).
- `adaptation` no perfil: meta de 50% dos bullets/competências na stack da vaga; `restack: false` numa experiência protege a stack original (`tailor.py: adaptation_context/stack_share`, regra 10 do prompt em `llm.py`).
- Resumo não cita anos totais em vagas júnior/pleno (datas visíveis); anos pela metade valem nas respostas de formulário.
- Template do currículo: `resume/templates/modern.html` (Inter em `templates/fonts`, foto via data URI, render por `file://` para as fontes carregarem).
- `skills.also_experienced` no perfil = tecnologias que o usuário declarou ter experiência; podem ir para Competências/headline, nunca para bullets de empresas onde o perfil não as lista (`tailor.py: validate_resume`).

## Regras do projeto
- Currículo gerado NUNCA inventa: só fatos de `config/profile.yaml`; `resume/tailor.py:validate_resume` é a barreira. Não afrouxar.
- Aplicamos para qualquer vaga de **desenvolvimento** independente de linguagem/nível; o classificador (`llm.py:classify_job`) decide "é dev?", não "é da minha stack?".
- Nunca tentar burlar captcha/Cloudflare: `browser.py:wait_for_human` para e espera o usuário.
- Respeitar ritmo/tetos em `settings.yaml:limits` (LinkedIn Easy Apply ~50/24h).
- Perguntas sem resposta viram `pending_questions` (DB) e depois `config/answers.yaml` (fonte: user > llm).

## Aprendizados de calibração (2026-09-09, LinkedIn/InHire reais)
- LinkedIn: botão de candidatura é um `<a>` com classes embaralhadas (texto "Candidatura simplificada" / "Candidatar-se", aria "Usar a candidatura simplificada..."); achar por papel+texto (`sources/linkedin.py: apply_button`), nunca por classe.
- Easy Apply renderiza o modal em **shadow DOM aberto**: `forms.py` usa `deepQuery` (atravessa shadow roots) no scan, nos botões e nos erros. `page.content()` não mostra o modal.
- Etapa "Currículo": lista de currículos salvos + `input[type=file]` com `display:none` ("Carregue o currículo"); `set_input_files` funciona; scan inclui inputs de arquivo mesmo escondidos.
- Checkbox "Marcar vaga como preferencial" (Premium) exige mensagem se marcado → regra `qa.py: NO_CHECK_RE` deixa desmarcado. Só termos/LGPD são marcados.
- Erros do formulário: só contam os que aparecem depois do clique e são visíveis de verdade (`forms.py: ERRORS_JS`), senão textos de acessibilidade viram falso erro.
- Candidatura externa do LinkedIn: link `linkedin.com/safety/go/?url=<site>` com target _blank; abrir a URL decodificada numa aba nova (`appliers/linkedin.py: _external_url`), não clicar.
  - Desde 2026-10 o botão "Candidatar-se no site da empresa" é um `<button>` SEM href: o clique abre o diálogo "Gostaria de compartilhar seu perfil?" cujo "Continuar" é o `<a safety/go?url=…>`. `LinkedInExternalApplier.apply` clica, procura o link com `_find_external_link` e abre a URL decodificada (verificado na Stone → Greenhouse, 2026-10-29).
- InHire (`<empresa>.inhire.app`): SPA (esperar render); "Candidatar-se para a vaga" abre painel lateral; etapa 1 dados (país e cidade são dropdowns react-dropdown-select com campo "Pesquisar" próprio), etapa 2 diversidade (checkboxes de grupos + selects react-dropdown-select cujas opções têm título + descrição: `forms.OPTIONS_JS` usa a PRIMEIRA linha como rótulo e marca `data-vagas-opt` para clicar; o rótulo do select vem da pergunta + `[name]`, nunca do placeholder), "Continuar inscrição" é `type=submit` (ENVIA). Depois abre **iframe `form-app.inhire.app/form?jobId=…&talentId=…`** (iframe-resizer: largura cheia e altura 0 até carregar → `_modal_frames` trata como "carregando" até 25 s) com questionário **Quill Forms** (`renderer-core`): tela "Iniciar", uma pergunta por bloco (`section[id^=block-]`, só o `.renderer-components-field-wrapper.active` conta para scan/botões), opções são `div.multipleChoice__optionWrapper` sem `<input>` (classe `selected` quando marcada; `SCAN_JS` agrupa como radio/multiselect), escolher uma opção avança sozinho (o loop refaz o scan até estabilizar), botão "OK" por bloco e "Enviar" no último; "pressione Enter ↵" é dica, não erro (`HINT_RE`). Sucesso: "Inscrição feita com sucesso! Respostas enviadas com sucesso!". A URL do iframe funciona sozinha (útil para depurar sem reenviar a candidatura).
- Gupy: login por subdomínio (`<empresa>.gupy.io/candidates/signin`). Senha + Turnstile NÃO funciona (nem manual). Caminho que funciona: `GupyApplier._login_via_linkedin` ("Entrar com LinkedIn" → `linkedin.com/uas/login` com `#username/#password` + `LINKEDIN_PASSWORD`, Enter como reserva do botão → "Permitir" → `/candidates/auth/linkedin`). A PRIMEIRA autorização pode voltar para o signin; repetir resolve, e depois o LinkedIn nem pede senha. A sessão Gupy não persiste entre execuções (loga de novo a cada vaga, rápido). Pós-login: tela "Olá Fulano, vamos continuar sua candidatura?" → Continuar (etapa sem campos: `apply()` inicia o fluxo se houver botão de avançar); links do menu ("Minhas candidaturas", "Empresas que me candidatei") casam com `APPLY_BTN_RE` → `APPLY_NEG_RE`/nav excluídos. Etapas: "Salvar e continuar" → "Perguntas criadas pela empresa" → "Responder agora" → perguntas (checkboxes MUI `checkbox-<id>-0/1/2` viram multiselect por prefixo do name; "Máx. 1000 caracteres" e "as respostas não poderão ser editadas" são avisos) → modal MUI "Enviar assim mesmo" (`BUTTONS_JS` prioriza `[role=dialog]`) → "Finalizar candidatura" → "Candidatura finalizada!". React re-renderiza botões entre scan e clique: `run_form_flow` reacha o botão e tenta 3x.
- Recrutei (`jobs.recrutei.com.br` → `talent.recrutei.com.br`): exige conta. A tela de CRIAÇÃO DE CONTA (signup) falha silenciosamente pelo robô; o usuário criou a conta manualmente (`vagas login --site recrutei`, 2026-09-10) e a sessão persiste no perfil. Logado: página da vaga → "Candidatar-se agora" → "Confirmar candidatura" (sem campos) → "Candidatura confirmada!". O currículo usado é o do perfil Recrutei (não há upload por vaga).
- Diversidade: regras determinísticas em `qa.py` (`DIVERSITY_SELECT_RULES`, `DIVERSITY_GROUP_RE`) a partir de `facts.gender_identity/sexual_orientation/race_color/diversity_groups` e `personal.disability`.

## Onde mexer quando um site quebra
- Primeira configuração/perfil: `setup.py` (assistente `vagas setup`, uma função por bloco de perguntas + `dump_profile`, que escreve o YAML com os comentários).
- Descoberta: `sources/linkedin.py` (CARDS_JS, LIST_SCROLL_JS), `sources/indeed.py` (CARDS_JS), `sources/gupy.py` (API pública).
- Candidatura: `appliers/linkedin.py` (modal Easy Apply), `appliers/indeed.py` (smartapply), `appliers/generic.py` (subclasses por ATS: só `apply_selectors`/`login_hosts`).
- Campos/botões/erros/sucesso: `forms.py` (SCAN_JS, BUTTONS_JS, SUBMIT_RE/NEXT_RE/SUCCESS_RE/ALREADY_RE/LIMIT_RE).
- Loop de etapas: `appliers/flow.py:run_form_flow`.
- Dumps de falha para diagnosticar: `data/learn/<ats>/<job>/stepN.{png,html,json}`.

## Redução de custo de IA (2026-09-10, depois de estourar os créditos)
Dia de referência: US$ 14,51 (274 chamadas de `tailor_resume` em gpt-4.1 = US$ 12,04 · 269 de `answer_questions` = US$ 1,94 · 369 de `classify` = US$ 0,40). 172 PDFs gerados para 111 candidaturas e 92 das chamadas de currículo eram retentativa.
- **Currículo preguiçoso:** `ApplyContext.resume` agora é uma FUNÇÃO (`pipeline.resume_for_upload`), resolvida só quando o formulário pede o arquivo. `ctx.resume_path` é property que gera uma vez e guarda; `ctx.has_resume` diz se há currículo SEM gerar. `forms.fill_field`/`upload_via_chooser` aceitam Path ou callable (`_resolve_resume`) e só resolvem no ramo de arquivo — `upload_via_chooser` acha o botão primeiro. Vaga que morre antes do formulário (login, anúncio expirado, botão sumido) não gasta gpt-4.1. `errors.ResumeBuildError` atravessa os `except Exception` largos de `forms`/`flow` para o pipeline devolver "currículo falhou" e recolocar na fila.
- **Competências sem IA:** `tailor.reorder_skills_for_stack` põe a stack da vaga na frente de `skills.main` e empurra o resto para `other`. `skills.main` só pode conter tecnologia que já está no perfil, então a fração era problema de seleção/ordem — 20 das 92 retentativas eram só por isso. Se ainda não bate a meta é porque o candidato não tem tantas tecnologias da vaga; retentar não resolveria.
- **Retentativa enxuta:** a 2ª chamada virou `llm.restack_bullets` — manda só os bullets já gerados + a lista de tecnologias permitidas (sem o perfil inteiro), pede o mesmo número de bullets e devolve `{"experiences":[{"company","bullets"}]}`. Experiência com `restack: false` fica de fora. Custa cerca de 1/5 de uma chamada completa.
- **Respostas de formulário:** perguntas repetidas na mesma leva de campos (o LinkedIn repete "Marcar vaga como preferencial") são perguntadas UMA vez e a resposta é copiada para as gêmeas; opções por pergunta caíram de 60 para 40 e `bank_hits` de 20 para 12; a descrição da vaga só é enviada quando há pergunta aberta (`OPEN_QUESTION_RE`).
